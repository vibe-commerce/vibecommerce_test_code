# lifecycle.md — жизненный цикл документа и знания

Last Updated: 2026-05-02

## Цепочка

```
backlog/ideas/  →  backlog/briefs/  →  backlog/plans/  →  код  →  documentation/
   (сырая          (зачем / scope     (как делать /          (реализация)   (факт)
    идея)            / AC)              чек-лист / риски)
                       │                       │                  │
                       ↓                       ↓                  ↓
                 archive/rejected/      archive/done/      archive/done/
                  (с причиной)        (после реализации)  (план + бриф)

Крупные фичи параллельно: _specs/<feature>/ (tech-spec, user-spec, ADR)
```

## Семантика трёх слоёв

| Слой | Главный вопрос | Что внутри | Чего быть НЕ должно |
|------|----------------|------------|---------------------|
| `ideas/` | «А что если?» | сырая мысль, гипотеза, контекст | scope, AC, чек-лист |
| `briefs/` | «Стоит ли делать?» | проблема, ЦА, цель, scope, AC | чек-лист задач, шаги реализации, риски подхода |
| `plans/` | «Как делать?» | подход, альтернативы, риски, чек-лист, метрика | дублирование «зачем» из брифа (только ссылка) |

**Сигнал «бриф пора превращать в план»:** появляется желание написать
секцию «План реализации» или «Чек-лист задач». Это чек-лист — значит
это уже план. Создай `plans/<slug>.md`, не пиши в брифе.

## Правила переходов

| Переход | Что делать |
|---------|-----------|
| `ideas/` → `briefs/` | Оформить идею в бриф (проблема, цель, scope, AC) по `_specs/templates/brief.md`. **Удалить** оригинал из `ideas/` или перенести в `archive/done/`. |
| `briefs/` → `plans/` | Создать план реализации по `_specs/templates/plan.md`. Бриф остаётся в `briefs/` до согласования плана. После старта работ — оба документа уезжают в `archive/done/` после релиза. |
| `briefs/` → `archive/rejected/` | Если бриф не прошёл приоритизацию — перенос с обязательной секцией «Почему отказались» по `_specs/templates/rejected.md`. |
| `plans/` → `_specs/<feature>/` | Только если фича крупная (>3 дней) и нужны tech-spec / user-spec / ADR. План остаётся в `plans/`, спецификации — в `_specs/<feature>/`. План ссылается на спеку. |
| `plans/` → код | Реализовать в `src/`. План остаётся в `plans/` до релиза, потом — в `archive/done/`. |
| `plans/` → `archive/rejected/` | Если план отвергнут на согласовании или прервана реализация. Обязательна секция «Почему отказались». |
| код → `documentation/` | Перенести **только факты о реализованном** в `documentation/NN-…` |
| → `archive/done/` | После релиза — бриф и план уезжают в архив для истории и референса из changelog. |

### Жёсткие правила

```
❌ НЕ пиши в documentation/ то, что ещё не реализовано
❌ НЕ держи в backlog/briefs/ план реализации (чек-лист, риски, подход)
❌ НЕ пиши в backlog/plans/ обоснование «зачем» (это в брифе, ссылка достаточна)
❌ НЕ удаляй отказанные брифы / планы — переноси в archive/rejected/ с «Почему»
❌ НЕ дублируй знание между ideas/briefs/plans/specs — только переходы со «съеданием» источника
```

## Когда план НЕ нужен (минимальные правки)

Лёгкие правки можно делать без плана-файла:

- опечатка / косметика / переформулировка одной строки;
- запрос на чтение / поиск / диагностику без изменений;
- единичная правка в одном файле <10 строк, явно описанная пользователем.

Сомневаешься — пиши план.

## Лёгкая фича без брифа

Если идея явно ценная и масштаб ≤1 день работы — допустимо пропустить
`briefs/` и сразу писать `plans/<slug>.md`. Бриф без плана — нормально
(фича в очереди приоритизации). План без брифа — нормально только для
лёгких фич; для крупных это риск делать «не то».

## Горизонты файлов

| Файл / папка | Горизонт жизни | Когда обновлять |
|--------------|----------------|-----------------|
| `backlog/ideas/` | дни-недели | Удаляй / переноси в archive после оформления в бриф |
| `backlog/briefs/` | недели | Уезжает в archive/done после релиза или archive/rejected при отказе |
| `backlog/plans/` | дни-недели | Активный план реализации; уезжает в archive/done после релиза |
| `backlog/archive/done/` | годы | Реализованные брифы и планы (история решений) |
| `backlog/archive/rejected/` | годы | Отказанные документы (с причиной + триггерами пересмотра) |
| `_specs/` | недели-месяцы | Только tech-spec / user-spec / ADR крупных фич |
| `documentation/` | месяцы-годы | Только факты о реализованном |
| `_changelogs/` | годами | После каждого релиза |
| `_status/` | актуально | После каждого деплоя |
| `AGENDA.md` | дни | В конце каждой сессии |
| `HANDOFF.md` | сессия | По триггеру `/handoff` |
| `FACTS.md` | годами | Раз в квартал-год |
| `ROADMAP.md` | кварталы | После каждой завершённой фазы |
| `_private/` | бессрочно | НИКОГДА не коммитить |

## Шаблоны для каждой фазы

В `_specs/templates/` лежат образцы:

**Lifecycle (для `backlog/`):**
- `brief.md` — приоритизация (зачем / scope / AC)
- `plan.md` — исполнение (подход / чек-лист / риски)
- `rejected.md` — оформление отказа

**Spec-driven (для `_specs/<feature>/`):**
- `user-spec.md` — требования глазами пользователя
- `tech-spec.md` — техническая спецификация
- `task.md` — задача
- `task-decomposition.md` — декомпозиция
- `skill-playbook.md` — для нового skill
- `design-system.md` — для дизайн-токенов
- `ADR-template.md` — Architecture Decision Record

При создании нового документа — копируй шаблон, не пиши с нуля.

## Принцип единого источника

- Каждый факт — в **одном** месте.
- Все остальные упоминания — через `[REF: path#section]`.
- При смене источника — `grep` по проекту, обнови ссылки.
- Дублирование → рассинхрон → invented facts → деградация знания.

## Antipatterns

- ❌ Идея в `_specs/` без оформления через бриф и план.
- ❌ Чек-лист задач в `briefs/<slug>.md` (это сигнал, что нужен `plans/<slug>.md`).
- ❌ План в `plans/` без брифа для крупной фичи (риск делать «не то»).
- ❌ Бриф остался в `briefs/` после релиза (должен быть в `archive/done/`).
- ❌ Отказанная идея удалена молча вместо `archive/rejected/` с «Почему».
- ❌ `_specs/<feature>/plan.md` дублирует `backlog/plans/<slug>.md` (план — только в `plans/`, спека — только в `_specs/`).
- ❌ Documentation-факт о фиче, которая ещё не реализована.
- ❌ Дублированный список фактов в 3 файлах вместо `[REF:]`.
- ❌ FACTS.md меняется каждую сессию (значит, это не FACTS, а AGENDA).
