# Handoff — End-of-session resume file

## Цель

Записать ОДИН файл `HANDOFF.md` в корне проекта, которого достаточно, чтобы новая сессия начала с того же места без переспрашиваний.

Это НЕ заменяет `AGENDA.md` (это рабочий контекст проекта вообще). Handoff — это срез «здесь и сейчас, продолжить завтра».

## Когда вызывается

Пользователь говорит вариант: «на сегодня всё, сохрани в handoff», «сделай handoff», «handoff», «заверши сессию» и т.п. — обычно в самом конце рабочей сессии.

## Алгоритм

### 1. Собрать контекст из текущей сессии

Перед записью посмотри:

```bash
git status
git log --oneline -10
git diff --stat
```

Проверь TodoWrite — есть ли незакрытые задачи. Если есть — это первый источник «что не доделано».

### 2. Архивировать предыдущий handoff (если есть)

Если в корне проекта уже лежит `HANDOFF.md`:

```bash
mkdir -p _handoffs
mv HANDOFF.md "_handoffs/$(date +%Y-%m-%d_%H-%M).md"
```

Так копится история handoff'ов без пересохранения «поверх».

### 3. Записать новый HANDOFF.md

Используй точно такой шаблон (заполни секции из контекста сессии):

```markdown
# Handoff — YYYY-MM-DD HH:MM

> Загрузи этот файл в новую сессию: «прочти HANDOFF.md и продолжи».

## Состояние репозитория

- Branch: `<branch>`
- Last commit: `<sha> <subject>`
- Uncommitted: <Да/Нет — короткий список файлов>
- Незакоммиченные ветки/стэши: <если есть>

## Что сделано в этой сессии

- <конкретное действие 1 — файл/коммит/решение>
- <конкретное действие 2>
- ...

## На чём остановились

<1–3 предложения: где курсор сейчас. Что было последним действием/попыткой. Какой файл/функция/тест/команда была в фокусе. Если работа в процессе — что именно проверяется/правится прямо сейчас.>

## Что не доделано

- [ ] <задача 1 — с указанием файла/функции если применимо>
- [ ] <задача 2>
- ...

## Следующие шаги (что делать в новой сессии)

1. <конкретный шаг 1 — команда/файл/действие>
2. <конкретный шаг 2>
3. ...

## Открытые вопросы / решения которые нужно принять

- <вопрос 1 — что неясно, какое решение ждёт пользователя>
- ...

## Важный контекст (то, что легко забыть)

- <гипотеза, которую проверяем>
- <обнаруженный баг/особенность>
- <конкретная команда/URL/конфиг которые понадобятся>

## Файлы которые надо открыть первыми

- `<path/to/file1>:<line>` — <зачем>
- `<path/to/file2>` — <зачем>
```

### 4. Подтвердить пользователю

В одно-два предложения: что записал в `HANDOFF.md`, сколько пунктов «не доделано», и что предыдущий handoff (если был) уехал в `_handoffs/`.

## Принципы

- **Конкретика > общие фразы.** Не «работали над тестами», а «добавили 3 теста в `tests/test_summarizer.py::test_arbiter_merge`, один падает на assert по `meeting_tags`».
- **Указывай файлы и строки** где можно — будущему «себе» это сильно ускорит вход.
- **Не дублируй AGENDA.md.** Handoff — про «эту сессию и следующий старт», AGENDA — про проект в целом.
- **Не пиши коммитов/PR-описаний** в handoff. Это не release notes.
- **Если сессия была короткой/без действий** — всё равно запиши, но честно: «обсуждали X, кода не писали, договорились Y».
- **Не коммить HANDOFF.md в git без явной просьбы.** Это рабочий артефакт, не часть истории кода. (Пользователь сам решит, нужен ли `_handoffs/` в `.gitignore`.)

## Чего НЕ делать

- Не запускай длинные операции «для отчёта» (тесты, сборки) — handoff это снимок состояния, а не финальная проверка.
- Не редактируй AGENDA.md в рамках handoff'а если пользователь не попросил — это отдельный протокол (см. CLAUDE.md «Конец сессии»).
- Не выдумывай «что было сделано». Если не помнишь — лучше короче и честнее.
