# `backlog/` — управление идеями, брифами, планами и задачами

Last Updated: 2026-05-02

## Жизненный цикл

С 0.5.0 lifecycle разделён на три семантических слоя + архив по исходу:

```
ideas/ → briefs/ → plans/ → код → documentation/
            │         │
            ↓         ↓
   archive/rejected/  archive/done/
```

| Слой | Главный вопрос | Что хранит | Когда переходит дальше |
|------|----------------|------------|------------------------|
| `ideas/` | «А что если?» | Сырые идеи, гипотезы | Идея пережила 1+ день и кажется ценной → в `briefs/` |
| `briefs/` | «Стоит ли делать?» | Проблема, ЦА, цель, scope, AC | Согласовали приоритет → в `plans/` |
| `plans/` | «Как делать?» | Подход, чек-лист, риски, метрика | Получили «делай» → в код |
| `archive/done/` | история решений | Реализованные брифы и планы | После релиза + changelog |
| `archive/rejected/` | почему не пошло | Отказанные документы (с причиной) | Сразу после решения «не делаем» |
| `tasks.md` | текущие задачи с приоритетами | оперативная очередь | Статус DONE → архивируй |

Шаблоны для каждого слоя — [`_specs/templates/`](../_specs/templates/README.md):
`brief.md`, `plan.md`, `rejected.md`.

## Сокращённый путь для лёгких фич

Лёгкая фича (≤1 день) — допустимо пропустить `briefs/` и сразу писать
`plans/<slug>.md`. Бриф без плана нормален (фича в очереди приоритизации);
план без брифа — только для лёгких фич, иначе риск делать «не то».

## Сигнал «бриф пора превращать в план»

В брифе появляется желание написать секцию «План реализации» или
«Чек-лист задач». Это план — создавай отдельный файл в `plans/`,
не дописывай в бриф.

## Жёсткие правила

```
❌ НЕ пиши чек-лист задач в backlog/briefs/<slug>.md
   (это сигнал создать backlog/plans/<slug>.md)
❌ НЕ пиши обоснование «зачем» в backlog/plans/<slug>.md
   (это в брифе; в плане — только ссылка на бриф)
❌ НЕ удаляй отказанные брифы / планы — переноси в archive/rejected/
   с обязательной секцией «Почему отказались»
❌ НЕ держи план реализации в _specs/<feature>/plan.md
   (план только в backlog/plans/; в _specs/ — tech-spec, ADR, user-spec)
```

## Формат задач (tasks.md)

| ID | Название | Приоритет | Статус | Дедлайн | Контекст |
|----|----------|-----------|--------|---------|----------|

Статусы: TO DO / WIP / DONE / ON HOLD
Приоритет: 1 = критично, 100 = когда-нибудь

## Управление

Используй `/project-manager` для спринтов, приоритизации, декомпозиции.
Используй `/architect` для генерации плана сразу в `plans/<date>-<slug>.md`
по шаблону.
