# `backlog/briefs/` — оформленные брифы (зачем / стоит ли делать)

Last Updated: 2026-05-29

## Что здесь

Брифы — оформленные идеи с понятной целью, scope и acceptance criteria.
Это слой **приоритизации**: решаем, стоит ли делать, до того как
расписывать «как».

Главный вопрос брифа: **«Стоит ли делать?»**. Если в брифе появляется
чек-лист задач или шаги реализации — это сигнал создавать `plan.md`
в [`../plans/`](../plans/), не дописывать в бриф.

## Зачем отдельный слой от плана

Brief смешивался с планом — это размывало семантику и приводило
к гибридным «брифам-планам». Теперь чётко разнесены: бриф для
приоритизации, план для исполнения.

## Как пользоваться

- **Создание:** перенос из `../ideas/<slug>.md` по шаблону
  [`../../_specs/templates/brief.md`](../../_specs/templates/brief.md).
- **Структура брифа:** проблема, целевая аудитория, цель, scope
  (в scope / вне scope), acceptance criteria, открытые вопросы /
  риски приоритизации.
- **Чего НЕ должно быть в брифе:** чек-листа задач, шагов реализации,
  рисков подхода, технических альтернатив. Это всё — в `plan.md`.
- **Промоут в план:** создаёшь `../plans/<slug>.md` по шаблону
  [`../../_specs/templates/plan.md`](../../_specs/templates/plan.md).
  Бриф остаётся в `briefs/` до релиза.
- **После релиза:** бриф уезжает в `../archive/done/`.
- **При отказе:** бриф уезжает в `../archive/rejected/` с секцией
  «Почему отказались» по шаблону `rejected.md`.
- **Промоут в спецификацию:** для крупных фич (>3 дней) — рядом с
  планом создаётся `_specs/<feature>/` с tech-spec/user-spec/ADR.
