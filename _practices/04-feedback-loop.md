# Feedback Loop — lint / test / fix / repeat

Last Updated: 2026-05-01

> Только зелёные тесты считаются концом разработки.
> Цикл фикса не может крутиться больше 3 итераций без переосмысления.

## Базовый цикл

```
        ┌──────────────┐
        │ make lint    │
        └──────┬───────┘
               ▼
       ┌───────────────┐         ┌─────────────┐
       │   PASS?       │── НЕТ →│  Исправь    │
       └──────┬────────┘         │  и повтори  │
              │ ДА                └──────┬──────┘
              ▼                          │
        ┌──────────────┐                 │
        │ make test    │←────────────────┘
        └──────┬───────┘
               ▼
       ┌───────────────┐         ┌─────────────┐
       │   PASS?       │── НЕТ →│  Исправь    │
       └──────┬────────┘         │  и повтори  │
              │ ДА                └──────┬──────┘
              ▼                          │
        ┌──────────────┐                 │
        │ make test-e2e│←────────────────┘
        │ (если есть)  │
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │ ✅ Готово    │
        └──────────────┘
```

## Команды

| Уровень | Команда | Что проверяет |
|---------|---------|---------------|
| Стиль | `make lint` | ruff / eslint / prettier — формат и анти-паттерны |
| Типы | `make typecheck` (если есть) | mypy / tsc — типобезопасность |
| Unit | `make test` | pytest / vitest — изолированные функции |
| Integration | `make test-int` (если есть) | взаимодействие компонентов |
| E2E | `make test-e2e` | полные пользовательские сценарии |
| Smoke | `./scripts/smoke-test.sh local` | живая проверка ключевых эндпоинтов |

**Скилл-обёртка:** `/test` — запускает все актуальные уровни одной командой.

## Правило 3 итераций

Если за **3 попытки** «фикс → запуск → провал» цикл не сходится —
**стоп**. Это сигнал, что:

- Подход в плане неверный → переосмыслить план
- Тест проверяет не то, что должен → починить тест отдельно
- Есть скрытая зависимость / окружение → изучить системно
- Симптом != причина → диагностировать root cause

В любом случае — **записать в** `.claude/data/error-log.md` (через
правило `error-learning`):
- Симптом (что упало)
- Что пробовал (3 попытки кратко)
- Гипотеза о root cause
- Следующий шаг

После записи — взять паузу 15+ минут или переключиться на другую
задачу.

## Что НЕ считать «зелёными тестами»

- ❌ «Запустил один файл вручную, не упало» — это не тест.
- ❌ «Тест запустился, но я закомментировал упавшие assert'ы» — это
   не тест, это саботаж.
- ❌ «Тест прошёл, но я знаю что фича работает не до конца» — задача
   не закрыта, пиши тест на пропущенный кейс.
- ❌ «Линтер с warning, но ничего критичного» — fix всё, что красное,
   обоснуй каждое подавление.

## Связка с этапом 6 (QA)

`make test` ≠ «фича работает».
Тесты проверяют **корректность кода**.
QA проверяет **корректность фичи** с точки зрения пользователя.

Оба этапа обязательны.
- Зелёные тесты + сломанная фича → плохие тесты (или нет покрытия).
- Красные тесты + рабочая фича → плохой код (или регрессия).

## Скиллы

- `/test` — единая команда запуска всех уровней
- `/qa-tester` — этап 6, не этап 5 — но связан
- `/techdebt` — анализ технического долга после провалов

## Антипаттерны

❌ **Закомментировать упавший тест, чтобы зелёный статус.** Если тест
   врёт — починить тест. Не глушить.
❌ **`--no-verify` при коммите.** Pre-commit упал не просто так.
❌ **Пушить с red CI и обещать «потом починю».** Не починишь.
❌ **Бесконечный фикс-цикл без записи в error-log.** Тратится
   контекст, ничего не закрепляется.
