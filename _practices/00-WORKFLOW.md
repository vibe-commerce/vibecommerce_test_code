# Полный workflow разработки — 8 этапов

Last Updated: 2026-05-02

Главный документ для любой задачи. Каждая фича / правка / эксперимент
проходит **все 8 этапов**, без пропусков. Если этап «не нужен» — это
обычно сигнал, что либо задача недоопределена, либо ты пропускаешь
важный шаг.

```
┌────────────────┐    ┌──────────────┐    ┌────────────┐
│ 1. ИДЕЯ        │───→│ 2. ПЛАН      │───→│ 3. РЕВЬЮ   │
│   backlog/     │    │   план в     │    │   плана    │
│   ideas/       │    │   файл       │    │            │
└────────────────┘    └──────────────┘    └────────────┘
                                                  │
                                                  ▼
┌────────────────┐    ┌──────────────┐    ┌────────────┐
│ 6. САМОТЕСТ    │←───│ 5. FEEDBACK  │←───│ 4. РАЗРА-  │
│   агентом      │    │   LOOP       │    │   БОТКА    │
│   (QA)         │    │   lint/test  │    │            │
└────────────────┘    └──────────────┘    └────────────┘
       │
       ▼
┌────────────────┐    ┌──────────────┐
│ 7. ДОКУМЕН-    │───→│ 8. PUSH В    │
│   ТАЦИЯ        │    │   GITHUB     │
│   /docs        │    │   /backup    │
└────────────────┘    └──────────────┘
```

## Этап 1 — Идея (capture)

**Что делается:** сырая мысль фиксируется в `backlog/ideas/<date>-<slug>.md`.

**Зачем:** идея может быть несвоевременной, дублирующей, невыполнимой.
Не дать ей сразу пожирать ресурс — но не потерять.

**Триггер перейти к Этапу 2:** идея прожила 1+ день, ты к ней вернулся,
выглядит достаточно ценной для оформления.

**Антипаттерн:** начинать кодить идею в день её появления.

---

## Этап 2 — Планирование в файл (Plan)

С 0.5.0 этап 2 явно делится на **две стадии** — каждая в своей папке.
Это устраняет смешение «зачем» и «как», которое раньше происходило
в одном брифе.

### 2a — Brief (зачем / стоит ли делать?)

**Что делается:** идея → `backlog/briefs/<date>-<slug>.md` по шаблону
[`../_specs/templates/brief.md`](../_specs/templates/brief.md).

**Что в брифе:** проблема, целевая аудитория, цель, scope (что
в scope / вне scope), acceptance criteria, открытые вопросы /
риски приоритизации.

**Чего в брифе быть НЕ должно:** чек-листа задач, шагов реализации,
рисков подхода. Это сигнал, что пора создавать `plan.md`.

### 2b — Plan (как делать?)

**Что делается:** согласованный бриф → `backlog/plans/<date>-<slug>.md`
по шаблону [`../_specs/templates/plan.md`](../_specs/templates/plan.md).

**Что в плане:** контекст, подход, отвергнутые альтернативы,
риски и митигации, чек-лист реализации, метрика «успех».

**Когда нужна спецификация в `_specs/<feature>/`:** если фича крупная
(>3 дней) и нужны архитектурные документы (tech-spec, user-spec, ADR).
План остаётся в `backlog/plans/<slug>.md` и ссылается на спеку.

### Сокращённый путь для лёгких фич

Лёгкая фича (≤1 день, явно ценная) — допустимо пропустить `briefs/` и
сразу писать `plans/<slug>.md`. Бриф без плана нормален (фича в очереди
приоритизации); план без брифа допустим только для лёгких фич.

**Скилл:** [`/architect`](../.claude/skills/architect/SKILL.md) — после
анализа архитектуры пишет план сразу в `backlog/plans/<date>-<slug>.md`
по шаблону.

**Подробнее:** [01-plan-then-act.md](01-plan-then-act.md)

**Антипаттерны:**
- «у меня план в голове, начну писать код»;
- чек-лист задач в `briefs/<slug>.md` (это сигнал создать `plans/<slug>.md`);
- план в `_specs/<feature>/plan.md` (план только в `backlog/plans/`).

## Этап 3 — Ревью плана (Validate)

**Что делается:** план читается **не тем, кто его писал**.

- Если работаешь один → пауза 30+ минут, потом перечитай свежим взглядом
- Если есть второй человек/агент → отдай на ревью

**Скилл:** `/architect` (повторно с пометкой «отревьюй этот план»),
или Tech Lead агент из `agent-teams:tech-lead`

**Что проверяем:**
- Цель = одна и измерима?
- Чек-лист задач — каждая задача выполнима за один заход?
- Риски — есть ли неучтённые?
- Может ли быть проще? (KISS)
- Не делаем ли мы YAGNI-фичи на будущее?

**Триггер перейти к Этапу 4:** план одобрен (явное «исполняй»).

**Антипаттерн:** AI говорит «приступаю» сразу после написания плана,
без подтверждения от человека.

---

## Этап 4 — Разработка

**Что делается:** идём по чек-листу плана сверху вниз.

**Правила:**
- Один пункт чек-листа = один логический коммит (можно не пушить сразу)
- При отклонении от плана — **обновляем план**, не молча отклоняемся
- Не делаем больше, чем в плане (анти-scope-creep)
- Используем существующие паттерны кода (изучи 1-2 похожих места перед
  написанием нового)

**Триггер перейти к Этапу 5:** все пункты чек-листа закрыты.

**Антипаттерн:** «пока правил X, заодно отрефакторил Y».

---

## Этап 5 — Feedback Loop (lint / test / fix)

**Что делается:** локальная самопроверка кода.

```
1. make lint     → если падает, исправь, повтори
2. make test     → если падает, исправь, повтори
3. make test-e2e → если есть e2e
```

**Скилл:** `/test` — запускает все три

**Правило 3 итераций:** если за 3 попытки не сходится — **остановись**,
зафиксируй проблему в `.claude/data/error-log.md` (через rule
`error-learning`), переосмысли подход. Не крути цикл «фикс → провал»
больше 3 раз — это сигнал об ошибке в плане.

**Подробнее:** [04-feedback-loop.md](04-feedback-loop.md)

**Антипаттерн:** «тесты упали, но я знаю что код правильный, закоммичу
и пофикшу позже».

---

## Этап 6 — Самотестирование агентом (QA)

**Что делается:** проверка не только что код правильный, а что **фича
работает с точки зрения пользователя**.

- Для UI / веб → `/qa-tester` (HTTP smoke + контент + Playwright
  визуальная проверка)
- Для API → curl / smoke-tests из `scripts/smoke-test.sh`
- Для бэкенда → integration-тесты + проверка golden path

**Чек:**
- Golden path: основной сценарий пользователя проходит?
- Edge cases: пустой ввод, невалидный ввод, race conditions?
- Регрессии: старые фичи не сломались?

**Триггер перейти к Этапу 7:** все три кейса — да.

**Антипаттерн:** считать `make test` зелёным концом проверки. Тесты
проверяют **корректность кода**, не **корректность фичи**.

## Этап 7 — Документация

**Что делается:** обновление документации **до коммита**.

**Скилл:** `/docs` (обновляет `_status/`, `_changelogs/`, `documentation/`,
`PENDING_RELEASE.md`)

**Что обновить:**
- `documentation/` — факты о новой фиче (если затрагивает архитектуру,
  ошибки, тесты, деплой)
- `_changelogs/local.md` — запись о фиче
- `VERSION` — bump по semver если значимое изменение
- `AGENDA.md` — что сделано в этой сессии
- `_specs/<feature>/` — финальное состояние спеки (если расходится
  с реализацией)

**Подробнее:** [05-document-and-backup.md](05-document-and-backup.md)

**Антипаттерн:** «закоммитил → теперь напишу документацию» (она потом
не пишется никогда).

---

## Этап 8 — Push в GitHub

**Что делается:** локальные коммиты уезжают на remote.

**Скиллы:**
- `/commit` — генерирует осмысленный commit message
- `/push` — пушит с подтверждением
- `/backup` — оба сразу одной командой
- `/cherry-pick` — переносит в `dev` для тестирования
- `/deploy-dev` → `/deploy-prod` — деплой

**Правила:**
- НЕ коммитить без подтверждения пользователя
- НЕ использовать `git add .` — добавлять файлы по одному
- НЕ коммитить `.env`, `_private/` (целиком — все подпапки)
- Conventional commits: `<type>(<scope>): <description>`

**Триггер «задача закрыта»:** код в `local`, запушен на GitHub,
документация на месте, чек-лист плана полностью отмечен.

**Антипаттерн:** считать задачу законченной до push'а («у меня же
работает локально»).
