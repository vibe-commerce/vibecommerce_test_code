## Этап 7 — Документация

### Что обновлять и где

| Изменение | Где обновлять |
|-----------|---------------|
| Новый компонент / архитектурное решение | `documentation/10-ARCHITECTURE.md` |
| Новый тест / стратегия тестирования | `documentation/30-TESTING.md` |
| Новый шаг деплоя / окружение | `documentation/40-DEPLOY.md` |
| Решена бага / инцидент | `documentation/80-ERROR-REGISTRY.md` |
| Новые файлы в подпапке | README этой подпапки |
| Любое значимое изменение | `_changelogs/CHANGELOG.md` |
| Релиз / bump VERSION | `VERSION` + `_changelogs/CHANGELOG.md` |
| Текущий фокус сессии | `AGENDA.md` |
| Финал спецификации | `_specs/<feature>/` |

### Скилл `/docs`

Автоматизирует обновление **за один проход**:
- `_status/{LOCAL,DEV,PROD}.md`
- `_changelogs/{local,dev,prod}.md`
- `documentation/` (затронутые файлы)
- `PENDING_RELEASE.md`

**Когда запускать:** после прохождения этапов 5-6, перед коммитом.

### Принцип «факты, не планы»

`documentation/` содержит **только реализованное**.
Запрещено писать туда:
- «планируем добавить...»
- «в будущем будет...»
- «временно работает через X, потом перепишем»

Незавершённое → `backlog/` или `_specs/`.

### HANDOFF / FACTS / ROADMAP

| Файл | Когда обновлять |
|------|-----------------|
| `HANDOFF.md` | В конце сессии, если работа не закончена |
| `FACTS.md` | При изменении фундаментальных фактов проекта (бренд, команда, продукты) — раз в месяц-квартал |
| `ROADMAP.md` | При завершении фазы / появлении новой стратегической цели |
| `AGENDA.md` | В конце каждой сессии — текущий фокус |

## Этап 8 — Push в GitHub

### Минимальный путь (одна команда)

```bash
/backup    # commit + push с осмысленным message
```

### Развёрнутый путь

```bash
git status                    # проверить, что добавляется только нужное
git add <конкретные файлы>    # НЕ git add . / -A
/commit                       # сгенерировать commit message
/push                         # подтвердить push
```

### Conventional Commits

Формат: `<type>(<scope>): <description>`

Типы:
- `feat` — новая фича
- `fix` — багфикс
- `docs` — только документация
- `style` — формат, не меняет логику
- `refactor` — рефакторинг без изменения поведения
- `test` — тесты
- `chore` — рутина (зависимости, конфиги)

Примеры:
```
feat(auth): добавить magic-link авторизацию
fix(api): убрать лишний log.error на 200-ответах
docs(workflow): описать этап Feedback Loop в _practices/
chore(deps): bump tailwindcss 3.4 → 3.5
```

### Правила безопасности

- ❌ НЕ коммитить `.env`, `.env.*`, `_private/` (целиком),
  `credentials/`, любые ключи / токены
- ❌ НЕ использовать `git add .` или `git add -A`
- ❌ НЕ делать `git push --force` без явного «да» от пользователя
- ❌ НЕ делать `git reset --hard` без подтверждения
- ❌ НЕ amend коммиты, которые уже на remote
- ❌ НЕ skip pre-commit hook'и (`--no-verify`) без явного запроса

### Ветки

```
local (разработка) → cherry-pick → dev (тестирование) → merge → prod
main = архив
```

После push на `local`:
- Тестовая фича → `/cherry-pick` в `dev` → `/deploy-dev`
- Готовая фича → `/merge-to-prod` → `/deploy-prod` (с подтверждением)

После любой ветки-операции — **возвращайся на `local`**.

### Скиллы для git/deploy

- `/commit` `/push` `/backup` — базовые
- `/cherry-pick` `/merge-to-prod` — между ветками
- `/deploy-dev` `/deploy-prod` `/rollback` — деплой
- `/git-status` — состояние всех веток
- `/logs` — посмотреть на удалённой VPS

## Триггер «задача закрыта»

Все из списка должны быть ✅:
- Код в `local` ветке
- Запушен на GitHub
- `documentation/` обновлён
- `_changelogs/CHANGELOG.md` имеет запись
- Все галочки чек-листа из [03-development-checklist.md](03-development-checklist.md) закрыты

Без этого — **задача не закрыта**, даже если «фича работает».

## Антипаттерны

❌ **«Запушу позже».** Push после каждого закрытого пункта чек-листа,
   не «в конце дня».
❌ **«Документацию завтра».** Не успеешь — задача висит.
❌ **«Закоммичу всё одним большим коммитом».** История теряется,
   откатить сложно.
❌ **`/backup` без `/test` сначала.** Пушить красное — анти-паттерн.
